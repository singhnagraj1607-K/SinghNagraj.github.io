HRMS Attendance Normalization & Payroll Logic

CATEGORY: BRD / FRD SAMPLE

Sample FRD Excerpt — Biometric Attendance & Overtime Rule

Anonymized Sample
BRD Objective & Scope

Goal: Standardize shift attendance mapping, grace rules and exception handling before monthly payroll generation.

Scope: Biometric punch logs, rotating week-offs, split shifts, missing-punch queue, holiday overtime.

Technical Confirmation Note (480 vs 540 Minutes)

Existing company shift examples reference both 480 net working minutes (8 hrs) and 540 gross minutes (9 hrs including break). Threshold must be confirmed against client policy per shift code before sign-off.

Rule ID Functional Logic Written in Sample FRD Linked Test Verification
BR-HR-04 If Punch_Out falls between 00:01 and 04:00 AM on a night shift, map Attendance_Date to shift start date. Compute OT_Mins = MAX(0, Worked_Mins - Confirmed_Threshold) only when OT_Approved == TRUE. Verify single attendance day logged on shift start date, zero duplicate next-day absence flags, and correct unapproved OT suppression.
CATEGORY: USER STORIES & ACCEPTANCE CRITERIA

US-P2P-12: Quality Inspection Acceptance & Rejection Split on GRN

As a Warehouse Quality Inspector,
I want to record Accepted Quantity and Rejected Quantity separately on each partial or full GRN,
So that only QC-approved units enter sellable stock while rejected items trigger supplier return or debit follow-up.
AC-01: Partial Receipt & QC Split

GIVEN PO-1042 has 100 units open
WHEN 60 units arrive on GRN-01 and QC marks 57 Accepted + 3 Rejected
THEN Available Stock increases by 57, Reject Queue logs 3, and PO Open Qty updates to 40.

AC-02: Quantity Balance Guardrail

GIVEN a GRN line shows Received Qty = 60
WHEN Accepted (50) + Rejected (15) does not equal 60
THEN save is blocked with validation error: "Accepted + Rejected must equal Received Quantity."

CATEGORY: BUG REPORT & POSTMAN API TESTING EXAMPLE

Sample API Validation & Defect Ticket (3PL Shipment Webhook)

Postman API Test Spec (Beyond HTTP 200)

Endpoint: POST /v1/shipments/track

Auth Assumption: HMAC signature or Bearer token validated prior to parsing.

{
  "event_id": "evt_88412",
  "awb_no": "AWB99201",
  "status": "IN_TRANSIT"
}

Assertions: HTTP 200 alone is insufficient — verify (1) invalid token returns 401, (2) missing required keys return 400, (3) duplicate event_id does not insert duplicate rows, (4) transient 503 queues retry & logs error.

BUG-API-208 (Sample Defect) Severity: High

Retried webhook payload inserts duplicate shipment tracking records

Steps to Reproduce: Send identical event_id + awb_no payload twice within 5 seconds.
Actual Result: Two timeline entries saved and two status alerts fired.
Expected Result: Enforce unique idempotency key constraint; acknowledge safely without duplicate persistence.
